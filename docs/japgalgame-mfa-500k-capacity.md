# 50 万条 / 7 天 MFA 容量方案

50 万条在 7 天（604,800 秒）内处理完，端到端平均吞吐至少 **0.827 条/秒**，实际排程还要为筛除复查、错误恢复和共享盘波动留余量。`JapGalgame` 现有 CTC 清单为 6,423,108 对 WAV/TXT；若目标其实是全部样本，同样期限需至少 **10.62 条/秒**，不能把两个目标混同。此前同一游戏 50 条的热缓存试验为 41.77 秒（约 1.20 条/秒），但排除了首次共享盘复制和 ASR/CTC，也不能代表所有游戏的时长、G2P 冷启动和并发共享盘负载，因此不能据此承诺全量工期。

2026-09-30 当前串行作业的首批 50 条真实启动验证：`hybrid-report.json` 记录端到端 **366.39 秒**，其中 74 个内部候选的实际 `mfa align` 只有 **17.00 秒**；50 条中自动通过 13、筛除 37。约 **0.136 条/秒** 的串行速度若机械外推到 50 万条需 **42.4 天**；8 进程完美线性才约 **5.3 天**，留给共享盘竞争、复杂音频和故障的余量很小。这一批来自同一个游戏，不代表全库通过率或时长分布。当前主要耗时在对齐之外的输入准备、G2P/声调、复核和文件操作；已增加分阶段耗时记录，后续批次才能进一步定位。原单批入口把全部阶段缓存放在每批临时目录里，批次完成后即丢弃；现为每个工作分片设置持久缓存，同时在批后清理体积最大的 WAV 缓存，只保留可复用的前端/声调/G2P 等结果。此缓存优化仍需用新批次实测收益。

新入口 `tools/galgame_mfa_parallel.py` 用已在本机的 16 份 CTC 清单分片，不让八个进程重复遍历共享盘的 642 万目录项。每片有独立 SQLite 续跑记录、MFA 模型根目录、持久阶段缓存、日志和工作目录；一个分片内仍按批次一次 MFA 调用处理整段及 CTC 锚点两个候选。通过管线与最终声能/标点/轨道审计的 TextGrid 才发布到 `GalgameMFA/<游戏>/<相对路径>.TextGrid`。GPU 仍供 CTC 使用；MFA 主要扩展 CPU 工作进程，实际并发上限由共享盘吞吐测定，不按 GPU 数机械设定。更改并发数不改变每片的样本归属或已记录的通过/筛除状态。并行入口会拒绝与当前串行监督器同时运行，防止同名成品竞争发布。

**当前没有启动新的并行全量作业。** 当前串行监督器在 `.runtime/jobs/galgame-mfa-all/`，切换前必须先让它停止并保存状态。并行作业的状态目录独立，已有串行状态不会自动迁入；应先核对旧作业已发布的成品、筛除记录及哈希，制定迁移或明确重审范围。精确的 50 万样本选择规则尚待确定；直接指定 `--target-items 500000` 时，会按 16 份清单各取 31,250 个当时已完整且尚未记录的样本，**不等价于某个外部给定的 50 万条清单**。若样本集合必须固定，应先生成并审核对应的分片清单。

串行作业停止、目标清单确定后，执行入口为：

```bash
cd /home/user/JapanMFA
bash tools/run_japgalgame_mfa_parallel.sh --target-items 500000 --workers 8 --batch-size 500
```

批次结果和异常日志在 `.runtime/jobs/galgame-mfa-parallel/logs/`，总进度与实测条/秒、剩余天数在 `.runtime/jobs/galgame-mfa-parallel/status.json`。若 8 进程在连续代表性试跑中未达到至少 0.827 条/秒，或使 CTC 进度明显下降，应比较 4、8、16 进程的**总**有效吞吐、共享盘响应、失败率与 CTC 速度，再定并发数。任何估算都必须把预检、MFA/G2P、后处理、正式审核、共享盘发布和筛除项计入。自动审核通过率和人工音素准确率是不同指标，不能用后者的未知值冒充已验证。
